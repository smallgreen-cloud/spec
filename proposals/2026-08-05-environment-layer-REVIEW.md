## 二、提案人自審：事件數不等於因果權重（送審前自行查出）

提案的核心論證是「TOOL＋PLATACCT＝38 筆＝44%，所以契約對這些無效」。**用的是事件數，不是因果權重。**

把每筆事件關聯到它所屬 run 的最終結果：

| 類別 | 出現在**非 success** run | 出現在 success run | 比率 |
|---|---:|---:|---|
| TOOL | **2** | 18 | 10% |
| PLATACCT | **5** | 14 | 26% |
| **REPO** | **8** | 8 | **50%** |

**TOOL 事件有 18/20 出現在成功的 run 上**——agent 踩到了，然後繞過去了。真正與壞結果相關的是 REPO（唯一達 50% 的類別），而那正是契約與 adapter 已經在處理的層。

codex 獨立指出同一問題並補上兩點：同一根因會產生多筆連鎖事件（重複計數）；且人工分類若問的是「現有契約能否處理」，會把本可宣告的版本／權限／capability 誤分到環境類。agy 進一步指控分類有「為新 schema 找合理性而灌水」的動機——動機無從查證，但**方向與提案人自己的查核結果一致**，這一點不辯。

## 三、提案的兩個實質錯誤（codex 抓到，均成立）

1. **算術**：四個機制是 A11＋E8＋C5＋D4＋B4＝**32 筆**，不是文中的 34（34 是含 F 類 2 筆的總分類數）。而 37% 是用 32 算的——文字與數字自相矛盾。
2. **範例自我打臉**：提案的設計要點寫「探針必須無副作用」，示範的 R2 探針卻是 `POST /r2/buckets` **建立一個 bucket**。除了副作用，還有名稱碰撞與殘留資源風險，且「能建立」不等於配額與後續操作可用。

## 四、決定性分析：逐 run 因果鏈（依 codex 建議的方法）

資料集共 **5 輪非 success**。逐輪讀它們的卡點事件：

| run | 專案 | 結果 | 主要根因 | 四機制能改變結果嗎 |
|---|---|---|---|---|
| 17 | second-brain (B) | partial | E43 token 無 Vectorize 權限（capability 缺口）＋E44 上游降級只覆蓋讀路徑（**需改碼**） | ✗ A 能 30 秒偵測，但降級路徑本身要改碼才會動 |
| 19 | imgbed (B) | partial | E49 README 零部署指令＋E51 儲存後端矩陣全滅 | ✗ 帳號缺全部儲存後端，天花板就是 degraded |
| 20 | microfeed (B) | partial | E52 R2 硬依賴且上游零降級模式＋**E54 `--yes` 不涵蓋所有提示** | △ **D 能解 E54**，但 E52 仍封頂在 degraded |
| 21 | r2-explorer (B) | **failed** | E55 專案核心即 R2，帳號未啟用＝三路全阻 | ✗ 只能更快失敗 |
| 37 | second-brain (C) | partial | E84 AI 額度於 run 前已耗盡 | △ **A 能避免整輪浪費**，但結果是「拒絕」不是「成功」 |

**結論：四個機制沒有一個能把任何一輪非 success 轉成 success。** D 在 run 20 直接命中一個阻斷點，A 在 run 37 能避免整輪浪費——但兩者都不會讓那兩輪變成 success。

**5 輪中有 4 輪的主要根因是 capability 缺口**（Vectorize 權限、R2 未啟用、儲存後端全缺），這類東西探針只能更早說「不行」。

> 統計上的但書：n=5，任何排序都不具統計效力。本節是質性因果讀解，不是效果量。

## 五、審查逼出的更好答案：槓桿在降級 profile，不在探針

上表第四欄有個共同形狀：**4/5 的非 success 是「capability 缺口」，而它們的結果是 partial／D4-degraded 而非 failed——因為後來人工做出了降級 adapter。**

imgbed、microfeed、pastebin-worker、second-brain 四案，**都是靠降級 adapter 才變成可驗證的**。也就是說：把 partial 變成「可交付的降級成功」的東西，歷史上一直是**降級路徑**，不是探針。探針只是觸發器。

但三方一致指出現行 `degrade_to` 設計不安全：

- **提案人自審**：降級模式**沒有自己的驗收條件**——這正是 second-brain 那個 bug 的成因（契約寫「keyword-only 降級」，實際是全面停擺，沒有任何條款抓得到，E85）。**照現行設計做，等於把它要防的 bug 制度化。**
- **codex**：`degrade_to` 只是字串，未定義犧牲哪些功能、資料相容性、驗收門檻與回復路徑；應是**版本化、有限枚舉、預先實測的獨立 profile，具自己的 acceptance／遷移／teardown**；預設 block，只有使用者明確接受且全部斷言通過才記為 degraded success，**絕不併入 full success**；無可靠唯讀探針時回報 unknown。
- **agy**：降級模式通常未經原作者 CI 測試；多能力同時失敗會組合爆炸（2³）；且**違背使用者意圖**——部署 R2 圖床卻降成 KV，對使用者可能毫無價值。

**綜合後的正確設計**：

```
降級不是探針的一個欄位，是一個獨立的、版本化的部署模式：
  - 有限枚舉（不是任意組合），每個模式預先實測過
  - 自帶 acceptance.yaml（modes: full / degraded-kv-only / …）
  - 自帶 teardown 與（若可能）回復到 full 的遷移路徑
  - 預設 block；轉入降級需使用者明確接受
  - degraded success 與 full success 在服務卡與 Pack 中分列，永不合併
```

agy 主張「降級不該進標準，探針維持 pass/fail」——**不採納**：資料顯示降級 adapter 是四個專案唯一能被驗證的形式，禁掉等於放棄那四案。但 agy 的「違背使用者意圖」成立，故加入「需使用者明確接受」。

## 六、attribution 的正確設計（codex 版本，採納）

提案的 `attribution: environment` 由專案自行宣告——三方一致認為會被濫用。codex 的修正較完整，採納：

**專案只能宣告「需要哪些 capability」與「允許哪些降級」，不得宣告歸因。** environment 標籤由 harness 依不可覆寫規則產生，並保存 API 錯誤碼、工具版本、帳號狀態、時間戳。至少四分：

| 情境 | 歸因 |
|---|---|
| 已宣告需求，帳號缺該 capability | environment incompatibility |
| 可預見的需求卻未宣告 | **contract/repo defect** |
| 探針通過後才失敗 | 不得回填 environment |
| 證據不足 | unknown / disputed |

服務卡分列 **observed condition／proximate cause／responsible owner**，不用單一標籤免責。agy 補充的「探針不得是任意 shell，須用白名單化的唯讀原語」一併採納——這也順帶修掉第三節那個有副作用的範例。

## 七、修正後的優先序

三方原始排序：提案 A→E→C→D/B｜agy C→E→A→D/B｜codex E→B/D→C→A。**唯一共識是 A 不該第一。**

依逐 run 因果鏈（第四節）與槓桿分析（第五節）定案：

| 順位 | 項目 | 依據 |
|---|---|---|
| 1 | **降級 profile 化**（有限枚舉＋每模式自帶 acceptance＋使用者明確接受＋與 full success 分列） | 唯一在歷史資料上把 partial 轉成可交付結果的東西；且不做就會制度化 E85 那個 bug |
| 2 | **D 非互動不變量** | 唯一在非 success run 的因果鏈上直接命中的機制（run 20 / E54）。可判定寫法＝stdin `</dev/null` 斷言不 hang，非檢查旗標 |
| 3 | **可恢復／冪等的狀態調和器**（三方收斂的缺漏，見第八節） | 把半成品收斂到完成狀態，是唯一直接指向「更完整地成功」的機制 |
| 4 | **E 工具行為知識庫** | 複利，但需處理過期與誤命中（見第九節） |
| 5 | **C 效果斷言** | 修正 agy 的觀察：C 的實例 5 筆中 3 筆在 teardown，對首次部署成功率貢獻有限；但 E45／E36 在安裝期且屬毒性連鎖 |
| 6 | **A 環境探針** | 降為「降級 profile 的觸發器」與 fail-fast／歸因工具，不再作為獨立主打 |
| 7 | **B settle 語意** | 併入 #16 |

**排序準則也一併修正**：codex 指出「事件數×跨專案廣度」重複獎勵頻率、忽略阻斷率與可挽救性。改為 **預期可挽救 run 數 × 嚴重度 × 信心 ÷（成本＋風險）**。

## 八、三方收斂的缺漏機制：可恢復、冪等的狀態調和器

提案人與 codex 獨立指向同一件事（agy 指向部署後 E2E 驗收，但那大致已由 `acceptance.yaml` 的 user_acceptance 涵蓋，屬部分重複）。

**問題形態**：部署做到一半失敗，重跑撞 `already exists`，整輪重來。
實例：E45（auto-provision 中途失敗不寫回資源 ID → 重跑撞 10014）／E70（測試 fail 後不退出撞工具上限，D1 已建成需 `--reuse-d1` 重入，而該旗標不在罐頭指令內）／E36（漏裝套件到首次部署才爆）。

codex 的設計（採納）：先建資源依賴圖與唯一識別 → 讀取帳號現況產生 plan → 每步寫 state journal／checkpoint → 部分成功後能 **discover 或 adopt 已建立的資源**、依序續跑 → 必要時補償回滾。**以故障注入驗證**：在每個 provisioning 邊界強制中斷，確認重跑能收斂、無重複資源、不遺失 ID、且 teardown 仍可歸零。

> codex 的原話值得留著：「否則系統只是更會解釋失敗，並沒有更會完成部署。」

## 九、其餘採納與不採納

**採納**
- codex：E 的條目會過期與誤命中——知識庫條目須帶版本區間與「最後驗證日」，過期即降級為提示而非規則
- codex：B 與 D 不應綁成一項（兩者機制不同）
- agy：探針限定白名單唯讀原語，禁任意 shell
- agy：counter-audit 概念（同帳號其他專案能正常呼叫該資源 → 該探針寫錯）；但不採納其「懲罰加倍」的處置

**不採納**
- agy「降級不該進標準」——見第五節
- agy「提案偷換概念，把提高成功率換成 fail-fast」——提案在「誠實邊界」一節**明白揭露**了這件事。揭露不等於偷換。但實質批評成立：**提案確實沒有回答被交付的問題**，這由第四節的逐 run 分析定案，不需訴諸動機

**兩方都指出、必須照做的驗證紀律**（codex 表述較完整）：分別預註冊 **full success／degraded success／fail-fast accuracy／time-to-diagnosis／cleanup completeness** 五個指標後做 run-level 對照。在那之前，任何機制**最多只能宣稱對既有事件具回溯適用性**，不得宣稱效果。
